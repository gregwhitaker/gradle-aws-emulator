# AWS Emulator 1.0.385 compatibility audit

Audited tag: `v1.0.385`, commit `813af480bf7f16d5418b64e4f5644a74a7da11c5`.
Previous audit: `v1.0.367`, commit `129a3db1945ce884e6d0341e4d77e19b8efc9667`.
The [release notes](https://github.com/aws/aws-emulator/releases/tag/v1.0.385)
and source comparison between those commits informed this review. This record
does not replace the approving maintainer review required before merging.

## CloudFormation dispatch review

The inventory was derived from executable dispatch at the audited commit:

- [`provisioner_for`](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs#L1046) maps 150 exact resource names, including policy aliases. Its default arm returns `None`.
- [`owner_for`](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning.rs#L1011) contributes 71 additional names through direct comparisons and delegated `kind_of` dispatch. This includes all four literal IAM policy names and both API Gateway submodules, `access_control` and `request_validation`.
- [`Owner::create`](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning/owner.rs) routes these owners to service operations. The new schema-required-property check runs before provisioning and before updates. Creation refusals still fail the stack; they are not accepted as successful provisioning.
- The [unowned-type fallback](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning.rs#L2637) still records completion without calling a service. Names found only in the broader template/type inventory remain excluded.

The result is **221 native names**, with **nine additions and no removals**.
The existing dedicated dispatch families are unchanged; AppSync adds six names.
Nested `AWS::CloudFormation::Stack` remains in the source inventory but is
rejected by the plugin, leaving **220 accepted native types**. Metadata and the
previously reviewed wait-condition signal behavior remain separate exceptions.

### New provisioning paths

| Types | Reviewed service operations |
| --- | --- |
| `AWS::AppSync::GraphQLApi`, `GraphQLSchema`, `DataSource`, `Resolver`, `FunctionConfiguration`, `ApiKey` | [Dedicated AppSync handlers](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning/appsync_resources.rs) call `CreateGraphqlApi`, `StartSchemaCreation`, `CreateDataSource`, `CreateResolver`, `CreateFunction`, and `CreateApiKey` through the service's REST JSON routes. IDs come from service responses; schema readiness polls the service. Update/read/delete paths dispatch to AppSync as well. |
| `AWS::ACMPCA::Permission` | [CA permission handlers](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner/network_and_delivery/certificates_and_dns.rs#L399) call `CreatePermission`, `ListPermissions`, and `DeletePermission` for the actual CA/principal pair. |
| `AWS::Redshift::SnapshotCopyGrant` | [Snapshot-copy grant handlers](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner/redshift_snapshot_copy_grants.rs) call `CreateSnapshotCopyGrant`, `DescribeSnapshotCopyGrants`, and `DeleteSnapshotCopyGrant`. Redshift resolves the supplied KMS key. Changing the key of an existing grant is explicitly refused rather than silently ignored. |
| `AWS::XRay::Group` | [X-Ray group handlers](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner/xray_groups.rs) call `CreateGroup`, `GetGroup`, and `DeleteGroup`. The physical ID is the ARN returned by X-Ray; a missing returned identity fails provisioning. |

The new integration regression creates all nine types and reads them through
AppSync, ACM Private CA, Redshift, and X-Ray SDKs. It verifies schema readiness,
pipeline function references, a real KMS-backed grant, and an actual CA permission;
then checks no-op/cache reuse, an AppSync schema update, and stack deletion.
The CA is deliberately retained so an empty permission listing proves that the
permission itself was revoked. This establishes provisioning and the tested
lifecycle paths, not complete property or data-plane fidelity for every type.

### Retained restrictions and limits

- Transforms/macros, nested templates, custom providers, unknown types, and declaration-only types remain rejected before connecting. False conditions do not bypass validation.
- [`WaitConditionHandle` now has a signed signal-URL implementation](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning.rs#L2572). It is no longer accurately described as an empty acknowledgement. It remains outside the plugin's accepted catalogue: this upgrade does not certify those URLs' reachability, expiry, or signal lifecycle for plugin consumers.
- Existing S3/SQS/DynamoDB and Cognito CloudFormation lifecycle regressions remain. Cognito pool renaming with dependent resources, which failed in the previous audit, remains uncertified; the regression keeps the pool name stable and updates its app client.
- Renaming an AppSync API with dependent schema/data-source/API-key resources was observed to fail during update. The upstream handler only implements in-place schema updates; the other five kinds return `Ok(None)` from `update`. A regression verifies that this rename fails deployment and leaves the last successful outputs intact. Keep the API name stable when updating its schema.
- AppSync schema deletion is owned by its parent API, and several property/update cases are explicitly unsupported upstream. The catalogue records that create reaches provisioning, not that every update can succeed.

## Cognito issuer compatibility

The [new pool issuer implementation](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-cognitoidentityprovider-awscognitoidentityproviderservice/src/state/user_pool.rs#L368)
uses the pool's region and issuer configuration, independently of the host used
to reach the emulator. Original pools advertise
`https://cognito-idp.<region>.amazonaws.com/<poolId>`; `UPDATED` pools use the
`issuer-cognito-idp` hostname. Previously the issuer followed the local request
endpoint. Signing remains RS256.

The previous export constructed a loopback issuer, causing the example's valid
token request to return HTTP 401. `ExportCognitoConfigurationTask` now reads the
issuer from `/<poolId>/.well-known/openid-configuration` at the configured local
emulator endpoint. The separate `jwksUri` still points to that local endpoint.
The advertised issuer is used only for claim validation; advertised remote
discovery/JWKS URLs and HTTP redirects are never followed.

Discovery uses the emulator's trust store, retains hostname verification, bounds
response size and connection/read timeouts, and fails on missing or malformed
issuer metadata. It changes no JVM-wide TLS or credential settings. Unit coverage
includes original, updated, and older local issuers, invalid metadata, redirects,
untrusted certificates, and hostname mismatch. Real-emulator coverage compares
the exported issuer with the issued token and retains signed-token acceptance,
wrong-client/ID-token/tampering rejection, group authorization, refresh flows,
configuration-cache reuse, and cleanup on successful and failed consumers.

## Other compatibility evidence

The first complete CI run exposed an existing automatic-port selection race:
parallel projects selected the same available loopback port before Docker bound
either container. Startup now retries recognized Docker bind conflicts only for
automatically selected `DIRECT` ports, up to three attempts, removing the failed
container and its home between attempts. Deterministic tests cover occupied-port
recovery, exhausted attempts, fixed-port failures, and unrelated startup failures.
The parallel-project Docker regression also repeats with configuration-cache reuse.

The [SES v2 send path](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/send_email.rs)
still records messages internally and publishes simulated events; no SMTP relay
was introduced. [Template listing](https://github.com/aws/aws-emulator/blob/813af480bf7f16d5418b64e4f5644a74a7da11c5/services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/list_email_templates.rs)
remains implemented. The existing SES/report integration suites verify these
operations and strict metadata reporting.

The existing suites cover verified HTTPS, resource operations, managed failure
cleanup, development persistence, external and remote-Docker connections, and
configuration-cache reuse. The PR's **CloudFormation audit** and **Emulator
compatibility** checks verify the supported Java/Gradle matrix, publication
smoke checks, both plugins' Docker suites on AMD64/ARM64, and repeated basic
example runs. A passing audit-record test alone is not compatibility evidence.
