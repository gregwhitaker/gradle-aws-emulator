# AWS Emulator 1.0.471 compatibility audit

Audited tag: `v1.0.471`, commit `91eb64ca5a78a7d78f4748085e65681abc417e15`.
Previous audit: `v1.0.385`, commit `813af480bf7f16d5418b64e4f5644a74a7da11c5`.
The [release notes](https://github.com/aws/aws-emulator/releases/tag/v1.0.471)
and [source comparison](https://github.com/aws/aws-emulator/compare/v1.0.385...v1.0.471)
informed this review. This record does not replace the approving maintainer
review required before merging.

## CloudFormation dispatch review

The catalogue was derived from the new tag's executable dispatch, then compared
with the previous catalogue. It is not the broader CloudFormation schema/type
inventory:

- [`provisioner_for`](https://github.com/aws/aws-emulator/blob/91eb64ca5a78a7d78f4748085e65681abc417e15/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioner.rs#L1159) maps **168 exact names**, including both SQS and SNS policy aliases, up from 150.
- [`owner_for`](https://github.com/aws/aws-emulator/blob/91eb64ca5a78a7d78f4748085e65681abc417e15/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning.rs#L1108) adds **83 exact names**, up from 71. This review follows each delegated `kind_of`, including all four IAM policy literals and both API Gateway submodules. The additions are two EC2 rule types, five AppSync types across two new dispatch families, and five Cloud Map types.
- [`Owner::create`](https://github.com/aws/aws-emulator/blob/91eb64ca5a78a7d78f4748085e65681abc417e15/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning/owner.rs) checks the resource model before dispatching to service-backed handlers. The main catalogue's create arms also reach service operations. A failed service call remains a provisioning failure.
- The [unowned-type fallback](https://github.com/aws/aws-emulator/blob/91eb64ca5a78a7d78f4748085e65681abc417e15/services/service-com-amazonaws-cloudformation-cloudformation/src/state/provisioning.rs#L2794) still records completion without calling a service. Those declaration-only types remain excluded, even when a schema or service API exists for them.

The result is **251 native names: 30 additions and no removals**. Nested
`AWS::CloudFormation::Stack` remains in the source inventory for completeness
but is rejected by the plugin, leaving **250 accepted native types**. CDK
metadata and the existing wait-condition signal behavior remain separate
exceptions. Signed `WaitConditionHandle` URLs remain outside the catalogue;
this audit does not certify their reachability, expiry, or signal lifecycle.

### Runtime evidence and retained limits

`CloudFormationExpandedTypesIntegrationTest` exercises 13 newly audited types
through their owning SDKs:

- EventBridge bus/policy and SSM maintenance window/target: verify real service
  state, unchanged deployment/cache reuse, and a bus-description update. Retain
  the parents during stack deletion to prove the policy and target themselves
  were removed, then delete the retained parents explicitly.
- EC2 ingress/egress and all five Cloud Map types: verify rule direction/ports,
  namespace kinds, service ownership, instance attributes and discovery;
  update namespace/instance metadata; verify deletion through the service APIs.
  The SDK helper disables host-prefix injection so discovery stays on the local
  verified HTTPS endpoint.
- AppSync Event API/channel namespace: verify service-assigned identities,
  unchanged deployment/cache reuse, and stack deletion. A separate deployment
  confirms that renaming the API with its dependent namespace fails the update
  and leaves the last successful output file intact.

The runnable CloudFormation example also creates an EventBridge bus and submits
an event to it. Existing regressions retain S3/SQS/DynamoDB operations, Cognito
resource lifecycle, and the previous nine AppSync/ACM Private CA/Redshift/X-Ray
additions. The other 17 new types have source-dispatch evidence in this audit,
not new end-to-end service tests. The catalogue certifies that creation reaches
a service handler, not complete resource fidelity.

Transforms/macros, nested templates, custom providers, unknown types, and
declaration-only types remain rejected before connecting, including declarations
under false conditions. A different configured emulator version remains an
error. The existing GraphQL API rename regression still fails as expected with
dependent resources; schema updates with a stable API name pass. The new Event
API rename failure is another upstream limitation, even though its dedicated
handler has an update operation. Keep API names stable. Cognito pool renaming
with dependent resources remains uncertified.

Cloud Map refuses service-description updates in an API-only (HTTP) namespace
with `InvalidRequest`: `Service in API-only namespace cannot be updated.` The
regression keeps that service's definition stable while updating the namespace
description and instance attributes. A handler's existence does not override
the owning service's restrictions.

## Cognito issuer compatibility

The [pool issuer implementation](https://github.com/aws/aws-emulator/blob/91eb64ca5a78a7d78f4748085e65681abc417e15/services/service-com-amazonaws-cognitoidentityprovider-awscognitoidentityproviderservice/src/state/user_pool.rs#L342)
now stores the emulator endpoint used when the pool was created. A pool created
through the local endpoint advertises `https://<host>:<port>/<poolId>` and keeps
that issuer even when later requests arrive through a different hostname.
The regional issuer is a fallback for an emulator with no served endpoint.
[Token signing](https://github.com/aws/aws-emulator/blob/91eb64ca5a78a7d78f4748085e65681abc417e15/services/service-com-amazonaws-cognitoidentityprovider-awscognitoidentityproviderservice/src/state/tokens.rs#L205)
remains RS256.

`ExportCognitoConfigurationTask` already obtains the issuer from the local
OpenID discovery endpoint. Its implementation remains valid. The old
integration assertion hard-coded the regional hostname and failed before the
remaining lifecycle assertions could run. It now checks the local endpoint
and pool ID, then verifies that the issued JWT's `iss` agrees with the export.
Password/refresh flows, configuration-cache reuse, fixture conflicts and cleanup
remain covered. The Spring Security example retains signature, issuer, expiry,
token-use, client-ID, group, and tampering checks.

Discovery and JWKS requests remain local, use the emulator trust store with
hostname verification, and do not follow advertised remote URLs or redirects.
The existing discovery unit tests still cover both regional and local issuers,
malformed metadata, redirects, untrusted certificates, and hostname mismatch.

## SES and runtime compatibility

The [SES v2 send path](https://github.com/aws/aws-emulator/blob/91eb64ca5a78a7d78f4748085e65681abc417e15/services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/send_email.rs)
records messages, publishes simulated events, and can route accepted messages
to the emulator's local account-receiving facility. It does not introduce an
SMTP relay or external inbox delivery. `GetMessageInsights` remains a metadata
API, not a way to retrieve stored bodies.

[Template listing](https://github.com/aws/aws-emulator/blob/91eb64ca5a78a7d78f4748085e65681abc417e15/services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/ops/list_email_templates.rs)
remains implemented. The new [shared account template registry](https://github.com/aws/aws-emulator/blob/91eb64ca5a78a7d78f4748085e65681abc417e15/services/service-com-amazonaws-sesv2-simpleemailservice-v2/src/state/templates.rs)
means SES v2 also lists templates created through v1. The old documentation claim
that the two APIs have separate stores is no longer correct. Reports continue
to use v2 and record unsupported operations without inventing an empty result.
`TestRenderEmailTemplate` also has a real rendering implementation; the SES
integration regression verifies listing and an SDK-rendered preview. Templated
`SendEmail` still explicitly returns `NotImplemented`, so the plugin keeps its
simple/raw send workflow. Kinesis retains its tested JSON connection; no claim
about the newer emulator's CBOR fidelity is needed for that configuration.

No plugin lifecycle or TLS changes are needed for this upgrade. Compatibility
verification includes the complete build, both plugins' Docker suites,
development persistence, managed failure cleanup, external and remote-Docker
connections, reports, supported service operations, and two basic-example runs
checking configuration-cache reuse. CI repeats these checks on AMD64/ARM64 and
the supported Java/Gradle matrix, including publication smoke checks. Both
**CloudFormation audit** and **Emulator compatibility** must pass; the audit-record
test alone does not establish compatibility.
