# AWS Emulator 1.0.492 compatibility audit

The reviewed tag `v1.0.492` resolves to `c77c1dcdea74d430cfc2dbacc8107408e42ea92a`.
The previous audit covered `v1.0.471` at `91eb64ca5a78a7d78f4748085e65681abc417e15`.
AWS published the revision-1 RPM for both AMD64 and ARM64. [Release notes] · [Upstream comparison] · [Previous audit](1.0.471.md)

## CloudFormation catalogue

I enumerated the match arms in `provisioner_for`, including the SQS and SNS policy
aliases, then followed the direct comparisons and delegated `kind_of` matches in
`owner_for`. These include the IAM policy literals and the API Gateway and CloudFront
submodules. Applying the same enumeration to the previous tag reproduced its checked-in
catalogue exactly. [Built-in dispatch] · [Owner dispatch]

| Upstream tag | Built-in names | Dedicated names | Total | Accepted by the plugin |
| --- | ---: | ---: | ---: | ---: |
| `v1.0.471` | 168 | 83 | 251 | 250 |
| `v1.0.492` | 174 | 95 | 269 | 268 |

All 18 additions reach an owning service. The two inventories have no overlapping names,
and every previously catalogued name is still present. The plugin excludes nested stacks
because it cannot inspect their child templates. CDK metadata and the existing wait-condition
exception are handled separately. [Catalogue](../../plugin/src/main/resources/io/github/gregwhitaker/awsemulator/aws/cloudformation/provisioned-types-1.0.492.txt)

The upstream deployment loop records a completed resource when no provisioner owns the type.
I reproduced this on the packaged emulator by submitting an `AWS::SES::EmailIdentity` stack
directly to CloudFormation. Both the stack and the resource reported `CREATE_COMPLETE`.
SES `GetEmailIdentity` returned `NotFoundException` for the declared address. The Gradle
validator rejects that type before opening a connection, including under a false condition.
[Create dispatch and declaration-only fallback] · [Docker regression]

## Checks against the packaged emulator

I deployed all 18 additions through the plugin on Linux/ARM64 and read each one back
through its owning service over verified HTTPS. The reads used the identities returned
by the stacks or the names in the templates.

| Added resource types | Service evidence | Upstream create handler |
| --- | --- | --- |
| `AWS::CloudWatch::CompositeAlarm` | `DescribeAlarms` returned the declared composite rule and its updated description. Deleting the stack removed the alarm. | [Composite alarms] |
| `AWS::AutoScaling::ScalingPolicy` | `DescribePolicies` returned the policy on the stack's group with the declared adjustment. The stack's `Ref` matched the policy name. | [Scaling policies] |
| `AWS::BackupGateway::Hypervisor` | `GetHypervisor` accepted the exported ARN and returned the declared hypervisor name. | [Hypervisors] |
| `AWS::Batch::JobDefinition` | `DescribeJobDefinitions` returned the registered revision by ARN. It became `INACTIVE` after stack deletion. | [Job definitions] |
| `AWS::Bedrock::DataSource` | `GetDataSource` returned the declared source under the stack's knowledge base using the exported data source ID. | [Bedrock data sources] |
| `AWS::S3Tables::Namespace` | `GetNamespace` returned the declared namespace under the exported table bucket ARN. | [S3 Tables namespaces] |
| `AWS::Athena::WorkGroup`, `DataCatalog` | `GetWorkGroup` and `GetDataCatalog` returned the declared descriptions before and after the update. Both disappeared from the service listings after deletion. | [Athena resources] |
| `AWS::CloudFront::CachePolicy`, `OriginRequestPolicy`, `PublicKey`, `KeyGroup`, `CloudFrontOriginAccessIdentity` | Read each resource by its exported ID using the corresponding CloudFront get operation. The key group contained the ID of the public key created by the stack. | [CloudFront policies and keys] |
| `AWS::CloudFront::KeyValueStore`, `Function`, `ConnectionFunction`, `ConnectionGroup` | CloudFront returned the store ARN, the published function in the `LIVE` stage, and the connection function and group by their exported IDs. | [CloudFront functions, stores, and groups] |
| `AWS::CloudFront::MonitoringSubscription` | `GetMonitoringSubscription` returned enabled real-time metrics for the distribution created by the stack. | [CloudFront monitoring] |

The Docker suite repeats the create, update, and delete checks for the composite alarm,
both Athena types, and the CloudFront key-value store. The other 14 types had direct service
readback during this audit. These checks cover the listed properties and operations.
[Docker regression]

## Other compatibility findings

- **AppSync.** Renaming the fixture's GraphQL API now succeeds in place. AppSync returned
  the new name under the original API ID. The schema, function ID, and resolver pipeline
  were still present. An Event API rename with a dependent channel namespace still rolls
  back and the plugin preserves the previous output file. [Upstream GraphQL update] · [GraphQL regression] · [Event API regression][Docker regression]
- **Cognito.** The pool still advertises the issuer selected at creation, and access and ID
  tokens use RS256. The plugin reads discovery and JWKS over the local HTTPS endpoint.
  [Issuer implementation] · [Token signing]
- **SES.** I created a template through v1, listed and rendered it through v2, and confirmed
  that v2 `SendEmail` with stored template content returns HTTP 501 `NotImplemented`. The
  send path records accepted simple/raw messages and routes simulated delivery inside the
  emulator. [Template listing] · [SendEmail implementation]
- **Cloud Map.** The packaged service refused a description update for a service in an
  HTTP namespace with `InvalidInput`. The fixture updates namespace and instance metadata
  while retaining the service definition. [Docker regression]

The basic consumer ran twice on a fresh managed emulator each time and reused the Gradle
configuration cache on its second run. The PR's compatibility check also covers both plugins,
publication, the supported Java/Gradle matrix, and Docker on AMD64 and ARM64.
[PR checks](https://github.com/gregwhitaker/gradle-aws-emulator/pull/12/checks)
