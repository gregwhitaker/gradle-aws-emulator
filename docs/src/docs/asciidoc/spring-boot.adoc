= Spring Boot
include::_partials/attributes.adoc[]
:description: Run and debug Spring Boot applications with an AWS Emulator companion plugin.

The companion plugin `io.github.gregwhitaker.aws-emulator.spring-boot` adds `bootRunLocal` and `bootRunLocalDebug`. It automatically applies the base emulator plugin. Your application selects and applies `org.springframework.boot` and its Java or Kotlin JVM plugin.

The companion is a separate artifact, `io.github.gregwhitaker:gradle-aws-emulator-spring-boot`, released with the core plugin. It uses the application's Spring Boot task type and does not bring Spring Boot into your build transitively. Compatibility is tested with Spring Boot 3.5.16 and 4.1.2.

toc::[]

== Apply from a checkout

Use the xref:getting-started.adoc#apply-from-a-checkout[composite-build setup], then apply the companion:

[source,kotlin]
----
import io.github.gregwhitaker.awsemulator.aws.sqs.CreateSqsQueueTask

plugins {
    java
    id("org.springframework.boot") version "4.1.2"
    id("io.github.gregwhitaker.aws-emulator.spring-boot")
}

awsEmulator {
    port.set(0)
    springBoot {
        profiles.set(listOf("local"))
    }
}
tasks.register<CreateSqsQueueTask>("createApplicationQueue") {
    queueName.set("application-events")
}
----

[source,groovy]
----
import io.github.gregwhitaker.awsemulator.aws.sqs.CreateSqsQueueTask

plugins {
    id 'java'
    id 'org.springframework.boot' version '4.1.2'
    id 'io.github.gregwhitaker.aws-emulator.spring-boot'
}

awsEmulator {
    port.set(0)
    springBoot {
        profiles.set(['local'])
    }
}
tasks.register('createApplicationQueue', CreateSqsQueueTask) {
    queueName.set('application-events')
}
----

Plugin application order does not matter. Until both Spring Boot and Java are present, the companion exposes its settings and the base emulator tasks, without registering the Boot tasks or starting Docker.

== Automatic resource creation

Register resource-creation tasks with their required properties, as above. `bootRunLocal` and `bootRunLocalDebug` automatically discover those tasks in the application's project and run them before starting the application. The queue in this example needs no `setupTasks`, `dependsOn`, or mode configuration.

Automatic setup covers S3 buckets; SQS queues and DLQs; SNS topics and SQS subscriptions; DynamoDB tables and their initializers; SSM parameters; Secrets Manager secrets; EventBridge buses, rules, and targets; Kinesis streams; KMS keys and aliases; and CloudWatch log groups and streams.

xref:ses.adoc[SES identity, template, configuration-set, and event-destination tasks] also participate. Sending email and reading message insights require explicit dependencies.

Discovery uses the core `@AwsEmulatorSetupTask` annotation on resource task types. Subclasses inherit it. Annotate your own `AbstractAwsResourceTask` subclasses to opt them into discovery. Registration remains lazy, so tasks declared after the companion is applied are included.

The companion selects its runtime as the default for discovered resource tasks and their resource prerequisites when a local Boot task is selected. Explicit task dependencies determine ordering between resources; for example, a log-stream task should depend on its log-group task. Use additional `setupTasks` or `dependsOn` dependencies for message publishing, data fixtures, and custom preparation.

Explicit resource modes are respected. A conflicting mode fails with a configuration error before startup. For separate test-only resources, exclude those task names or paths:

[source,kotlin]
----
awsEmulator {
    springBoot {
        excludedSetupTasks.add("createTestQueue")
    }
}
----

Exclusions affect automatic discovery; explicit dependencies still run. To select all setup tasks manually, set `autoCreateResources` to `false` and use `setupTasks`. In that case, configure resource tasks to use `awsEmulator.springBoot.mode` yourself. Ordinary `bootRun`, test tasks, and standalone resource invocations retain their existing behavior.

== Run and debug

For applications in different Gradle projects, `awsEmulator.useSharedRuntime(":local-aws", "application")` selects one owner and automatically attaches its named resources to both local Boot tasks. No additional `springBoot.resourceSets` attachment is needed for those sets. The owner's settings govern the shared runtime; the application's `springBoot.mode` still selects managed or development. See xref:shared-runtimes.adoc[sharing across projects].

For resources shared with managed tests and scenarios, declare xref:scenarios.adoc#resource-sets[reusable resource sets] and attach them using `awsEmulator.springBoot.resourceSets.add(setProvider)`. The plugin creates separate tasks for each mode and runs provisioning and fixtures before either local Boot task. Generated resource-set tasks are excluded from automatic discovery, so test attachments do not leak into Boot setup. Explicit resource sets run even when `autoCreateResources` is false.

[source,shell]
----
./gradlew bootRunLocal
./gradlew bootRunLocal --args='--server.port=8081'
./gradlew bootRunLocalDebug
./gradlew stopAwsEmulator
----

The debug task listens on `127.0.0.1:5005` and waits for a debugger. The ordinary `bootRun` task is not connected to the emulator by applying this plugin.

Both local tasks use `BootRun`. They inherit `bootRun`'s main-class provider (including Spring Boot's automatic discovery), classpath, Java launcher, optimized-launch setting, working directory, environment, system properties, application arguments, JVM arguments, and argument providers when configured. Custom actions on `bootRun` are not copied. Configure the local task directly when it needs additional task behavior. Command-line `--args` overrides the copied application arguments.

The tasks support configuration-cache reuse. With automatic main-class discovery, Spring Boot can invalidate the first cache entry when a clean compilation creates class directories; subsequent unchanged runs reuse the cache.

The base plugin supplies endpoint, region, generated credentials, and TLS trust just before the JVM starts. Your application still declares its own AWS SDK dependencies. See xref:connections.adoc[Credentials and TLS] for connection details.

== Configuration

Configure the companion in `awsEmulator { springBoot { ... } }`. The previous top-level `springBootEmulator` block remains an alias for the same settings for compatibility with existing builds.

[cols="1,1,3",options="header"]
|===
|`awsEmulator.springBoot` property |Default |Behavior
|`mode` |`EmulatorMode.DEVELOPMENT` |Selects the persistent development instance or a build-owned `MANAGED` instance.
|`profiles` |`["local"]` |Adds `spring.profiles.active`; an empty list adds no profile argument.
|`jvmArgs` |`[]` |Additional JVM arguments for both local tasks.
|`autoCreateResources` |`true` |Automatically discovers resource-provisioning tasks and runs them before either local task.
|`excludedSetupTasks` |`[]` |Task names or paths to omit from automatic discovery.
|`setupTasks` |`[]` |Additional Gradle task names or paths that both local tasks depend on.
|`resourceSets` |`[]` |Reusable definitions to provision and seed in the application's selected mode.
|`debugPort` |`5005` |Debugger port, from 1 to 65535.
|`debugSuspend` |`true` |Whether the debug task waits for a debugger before starting the application.
|===

Resource setup tasks use the same runtime as the application. Reusable sets create separate tasks for consumers in different modes within one build. When using ordinary task instances instead, register separate tasks and exclude test-only resources from automatic discovery.

Development instances retain their resources across Gradle invocations until `stopAwsEmulator` or `restartAwsEmulator`. For automatic cleanup after the application finishes, including ordinary application failures:

[source,kotlin]
----
import io.github.gregwhitaker.awsemulator.model.EmulatorMode

awsEmulator {
    springBoot {
        mode.set(EmulatorMode.MANAGED)
    }
}
----

Hard process termination or Docker daemon failure can prevent cleanup, as described in xref:testing.adoc[Tests and Java execution].

== Runnable example

The link:{repo-url}/tree/main/examples/spring-boot[Spring Boot example] sends and receives an SQS message and exits. From this repository:

[source,shell]
----
./gradlew -p examples/spring-boot bootRunLocal --configuration-cache
./gradlew -p examples/spring-boot bootRunLocal --configuration-cache
./gradlew -p examples/spring-boot stopAwsEmulator
----

Use `-Pmanaged=true` for automatic cleanup, or `bootRunLocalDebug` to attach a debugger. Browse the link:spring-boot-api/index.html[companion Java API] for the extension reference.

== Spring Cloud AWS

The link:{repo-url}/tree/main/examples/spring-cloud-aws[Spring Cloud AWS example] pins Spring Cloud AWS 3.4.0 with Boot 3.5.16, following the https://github.com/awspring/spring-cloud-aws#compatibility-with-spring-project-versions[framework compatibility matrix]. It declares an `application` resource set once and attaches it to managed Spring tests, local Boot runs, and a development scenario.

[source,shell]
----
./gradlew -p examples/spring-cloud-aws test bootRunLocal --configuration-cache
./gradlew -p examples/spring-cloud-aws test bootRunLocal --configuration-cache
./gradlew -p examples/spring-cloud-aws stopAwsEmulator
----

The local profile imports required configuration before the application context starts:

[source,properties]
----
spring.config.import=aws-parameterstore:/spring-cloud-example/,aws-secretsmanager:/spring-cloud-example/credentials
spring.cloud.aws.endpoint=${aws.endpointUrl}
spring.cloud.aws.region.static=${aws.region}
spring.cloud.aws.parameterstore.endpoint=${aws.endpointUrl}
spring.cloud.aws.secretsmanager.endpoint=${aws.endpointUrl}
----

Gradle provisions the parameter and JSON secret before launch. Spring injects their values through `@Value`, including in `@SpringBootTest`. The application uses the auto-configured `SqsAsyncClient` and `SqsTemplate` to send messages, and `@SqsListener` consumes both seeded and newly sent messages. It waits for successful manual acknowledgements with bounded timeouts. The SDK reads generated credentials through its normal provider chain, and all clients use HTTPS with certificate and hostname validation enabled; no custom client beans or trust managers are needed.

The Docker suite verifies this framework path with configuration-cache reuse, separate managed and development instances in one build, and managed cleanup after test failures, application failures, and missing required imports. Spring Cloud AWS 4.x is outside this example's compatibility coverage; the direct SDK example separately covers Boot 4. See the https://docs.awspring.io/spring-cloud-aws/docs/3.4.0/reference/html/index.html[Spring Cloud AWS reference] for import and listener configuration.
