= Cognito User Pools and authentication
include::_partials/attributes.adoc[]

Create Cognito User Pools and public app clients, seed confirmed users and group memberships, and export runtime IDs for application tests or local development. Task types are in `io.github.gregwhitaker.awsemulator.aws.cognito` and use the `cognito-idp` service.

toc::[]

== Run the Spring Security example

[source,shell]
----
./gradlew -p examples/cognito test --configuration-cache
./gradlew -p examples/cognito test --configuration-cache
./gradlew -p examples/cognito bootRunLocal
./gradlew -p examples/cognito stopAwsEmulator
----

The tests use AWS SDK v2 password sign-in and refresh, then call a Spring Boot application with signed access tokens. They check anonymous rejection, group authorization, incorrect passwords, tampered signatures, ID tokens presented as access tokens, and tokens for another client. The second invocation reuses Gradle configuration and provisions a fresh managed runtime. `-PfailExample=true` intentionally fails the test to exercise managed cleanup.

IMPORTANT: AWS Emulator `1.0.322` signs Cognito tokens with *ES256*, while AWS Cognito signs with *RS256*. The example's `local` Spring profile explicitly allows ES256 and validates signature, issuer, expiration, `token_use=access`, and the configured `client_id`. HTTPS certificate and hostname verification stay enabled. Configure production Cognito separately with its real issuer and RS256 policy. This integration does not claim complete Cognito fidelity. See the https://github.com/aws/aws-emulator/blob/v1.0.322/services/service-com-amazonaws-cognitoidentityprovider-awscognitoidentityproviderservice/src/state/tokens.rs[upstream token implementation].

Supported workflows are User Pool provisioning, public clients, administrative user fixtures, groups, password sign-in, and refresh. Identity Pools, hosted login/OAuth authorization endpoints, federation, SRP, MFA, Lambda triggers, custom schema management, and confidential client creation are outside this initial integration.

== Tasks and defaults

All task types share `mode` (default `MANAGED`) and `apiCallTimeoutSeconds` (default `30`). They always execute against live state, with up-to-date skipping and build-cache reuse disabled. Configuration-cache reuse is supported. Applying the plugin or listing tasks does not start Docker.

[cols="2,3",options="header"]
|===
|Task type |Properties and behavior
|`CreateCognitoUserPoolTask` |`userPoolName`. Creates a pool with service defaults or reuses a uniquely named pool without changing its settings.
|`CreateCognitoUserPoolClientTask` |`userPoolName`, `clientName`, `explicitAuthFlows`. Creates a public client (`GenerateSecret=false`), or reuses one with matching flows and no secret.
|`SeedCognitoUsersTask` |`userPoolName`, `fixtures` JSON file, `overwrite` (default `false`). Seeds users and additive group memberships.
|`ExportCognitoConfigurationTask` |`userPoolName`, `clientName`, `outputFile`. Exports current IDs and local connection URLs as JSON.
|`ListCognitoUserPoolsTask` |Lists all pool names and IDs, following pagination.
|`DeleteCognitoUserPoolTask` |`userPoolName`. Deletes the pool and its users, groups, and clients. Missing pools are a no-op; deletion protection and service errors remain failures.
|`DeleteCognitoUserPoolClientTask` |`userPoolName`, `clientName`. Deletes a client; a missing pool or client is a no-op.
|===

`explicitAuthFlows` defaults to `ALLOW_USER_PASSWORD_AUTH`, `ALLOW_ADMIN_USER_PASSWORD_AUTH`, and `ALLOW_REFRESH_TOKEN_AUTH`. It accepts a nonempty, unique subset of those three values. Reusing a client compares the complete set, ignoring order; conflicting flows or a client secret fail without modifying the client.

Pool and client IDs are generated by the emulator and resolved by exact name at execution time. Names are not assumed unique: more than one matching pool, or client within a pool, fails before selecting or deleting one. Use distinct names when configuring concurrent consumers. Client, fixture, and export tasks require their pool to exist; resource sets order the steps, or ordinary task registrations must declare `dependsOn`.

The convenience commands `listCognitoUserPools`, `deleteCognitoUserPool`, and `deleteCognitoUserPoolClient` default to `DEVELOPMENT`. They accept `--mode=MANAGED`; the deletion commands also accept `--userPoolName` and, for a client, `--clientName`:

[source,shell]
----
./gradlew -p examples/cognito seedAwsEmulator
./gradlew -p examples/cognito listCognitoUserPools
./gradlew -p examples/cognito deleteCognitoUserPoolClient --userPoolName=example-users --clientName=example-app
./gradlew -p examples/cognito deleteCognitoUserPool --userPoolName=example-users
./gradlew -p examples/cognito stopAwsEmulator
----

== Reusable setup with Kotlin DSL

Apply the core plugin and Java plugin, then configure a resource set:

[source,kotlin]
----
import io.github.gregwhitaker.awsemulator.aws.cognito.*
import io.github.gregwhitaker.awsemulator.model.EmulatorMode

val auth = awsEmulator.resourceSets.register("auth") {
    provision("pool", CreateCognitoUserPoolTask::class.java) {
        userPoolName.set("app-users")
    }
    provision("client", CreateCognitoUserPoolClientTask::class.java) {
        userPoolName.set("app-users")
        clientName.set("app")
    }
    seed("users", SeedCognitoUsersTask::class.java) {
        userPoolName.set("app-users")
        fixtures.set(layout.projectDirectory.file("fixtures/users.json"))
    }
    seed("configuration", ExportCognitoConfigurationTask::class.java) {
        userPoolName.set("app-users")
        clientName.set("app")
        outputFile.set(layout.buildDirectory.file(mode.map {
            "cognito/${it.name.lowercase()}.json"
        }))
    }
}
val tests = tasks.named<Test>("test") {
    systemProperty("example.cognito.configuration",
        layout.buildDirectory.file("cognito/managed.json").get().asFile.absolutePath)
}
awsEmulator {
    useWith(tests, EmulatorMode.MANAGED, auth)
    scenarios { register("default") { resources(auth) } }
}
----

When the xref:spring-boot.adoc[Spring Boot companion] is applied, add `awsEmulator.springBoot.resourceSets.add(auth)`. Configure `bootRunLocal` and `bootRunLocalDebug` with your application's configuration-file property pointing to `build/cognito/development.json`. The runnable example demonstrates both tasks. The property `example.cognito.configuration` belongs to that example's reader; the plugin does not automatically configure Spring Security or application properties.

The provisioning, fixture, and export task types carry `@AwsEmulatorSetupTask` for the companion's ordinary-task auto-discovery. Resource-set instances use explicit resource-set attachment instead. Separate managed and development output files prevent one runtime's configuration from overwriting the other's.

== Ordinary tasks with Groovy DSL

[source,groovy]
----
import io.github.gregwhitaker.awsemulator.aws.cognito.*

def pool = tasks.register('createAuthPool', CreateCognitoUserPoolTask) {
    userPoolName.set('app-users')
}
def appClient = tasks.register('createAuthClient', CreateCognitoUserPoolClientTask) {
    dependsOn(pool)
    userPoolName.set('app-users')
    clientName.set('app')
}
def users = tasks.register('seedAuthUsers', SeedCognitoUsersTask) {
    dependsOn(appClient)
    userPoolName.set('app-users')
    fixtures.set(layout.projectDirectory.file('fixtures/users.json'))
}
def config = layout.buildDirectory.file('cognito/managed.json')
def exported = tasks.register('exportAuth', ExportCognitoConfigurationTask) {
    dependsOn(users)
    userPoolName.set('app-users')
    clientName.set('app')
    outputFile.set(config)
}
def tests = tasks.named('test') {
    dependsOn(exported)
    systemProperty('example.cognito.configuration', config.get().asFile.absolutePath)
}
awsEmulator { useWith(tests) }
----

For ordinary task registrations targeting a persistent instance, select `EmulatorMode.DEVELOPMENT` on every resource task in the dependency chain and choose a development-specific output path.

== User fixtures and repeat runs

.fixtures/users.json
[source,json]
----
[
  {
    "username": "alice",
    "password": "Local-Test123!",
    "attributes": {"email": "alice@example.test", "email_verified": "true"},
    "groups": ["admins"]
  }
]
----

The file is a nonempty JSON array, limited to 16 MiB. Each entry requires `username` and `password`; `attributes` is an optional string-to-string object, and `groups` is an optional array of unique group names. Unknown fields, duplicate JSON keys, duplicate usernames, invalid shapes, and the immutable `sub` attribute are rejected before the seeding task opens its connection or modifies users. The service enforces its password policy and supported attribute names. Use local test credentials; passwords are read during execution and are not printed.

New users are created with invitations suppressed and a permanent password, making them confirmed without an email/SMS confirmation flow. Missing groups are created with default settings; memberships are added. Existing group settings, unrelated attributes, users, and memberships are preserved.

With `overwrite=false`, an existing enabled, confirmed user is reused only when all explicitly requested attributes match. The existing password is retained: Cognito cannot return a password for comparison, so changing only the fixture password has no effect on a reused user. With `overwrite=true`, supplied attributes are updated and the permanent password is reset on each run. Disabled users always fail and require explicit re-enabling. An existing unconfirmed user requires `overwrite=true` to set its permanent password.

All entries are parsed and validated before SDK calls. Service failures can leave earlier entries or a newly created user in place; errors report the failing entry number and completed count without fixture values. After fixing a failure during password assignment, rerun with `overwrite=true` to complete the user. The task does not roll back or delete unrelated resources.

== Consume generated configuration

`ExportCognitoConfigurationTask` writes these fields:

[cols="1,3",options="header"]
|===
|Field |Meaning
|`userPoolId` |The selected pool's actual ID.
|`clientId` |The selected app client's actual ID.
|`region` |The runtime's configured region.
|`endpoint` |The local HTTPS SDK endpoint.
|`issuer` |The local endpoint followed by `/userPoolId`.
|`jwksUri` |The issuer followed by `/.well-known/jwks.json`.
|===

The output contains no credentials, passwords, tokens, or client secrets. It is replaced atomically where supported and uses owner-only permissions on POSIX filesystems. The file survives the task; its IDs become stale when that emulator stops. Always depend on the export and read it in the consuming process after setup. Do not parse it during Gradle configuration or hardcode generated IDs. Each managed invocation exports fresh IDs, including when the configuration cache is reused.

Applications declare their own `software.amazon.awssdk:cognitoidentityprovider` dependency and use the xref:connections.adoc[normal SDK endpoint, credential, and TLS providers] supplied to opted-in consumers. The example reads this JSON in application code and configures `NimbusJwtDecoder` with the local JWKS URI. It does not disable JWT or TLS validation or modify the Gradle daemon's global settings.
